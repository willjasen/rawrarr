# Rawrarr device signing design note

## Purpose

Rawrarr will eventually need a way to distinguish authorized devices from arbitrary writers in a Syncthing folder. Device signing is a candidate integrity and authorship mechanism inspired by the enrollment-root model in the sibling Tephramesh project. Syncthing peer membership alone is not sufficient application authorization. The device identity should be unique and cryptographically verifiable across all nodes; the node function must be an explicit field rather than embedded in that identity.

The root-key client primitive and optional browser-local age-ID retention are implemented. Browser storage is limited to the age private ID after explicit opt-in; the instance root signing key is never saved there. The enrollment protocol, node credentials, signed shared records, and migration remain unimplemented; this design is not yet an end-to-end security feature.

## Candidate model

### Age identity ownership: user, node, and integration

Treat an age identity as a decryption principal, not as a person or device login. Rawrarr should distinguish three principal types:

- **User identity:** the user's recoverable age identity, created or imported in the browser and used to open the user's shared vault. The current design keeps it browser-local or, by explicit opt-in, on the user's node. It must not be sent to the coordinator or stored in a service-node path.
- **Node identity:** each subscriber node creates its own post-quantum age identity automatically on startup if one is not already present in its persistent, node-local protected storage (`/data/node-age-identity`). This applies to new and already-running environments: preserve any existing user/shared identity in `/data/age-identity` and create the separate node identity alongside it. Container replacement with the persistent data volume must retain the node identity. Never put its private identity in `/shared`, Syncthing, the coordinator, logs, or Compose environment/arguments. The node's public recipient can be published as authenticated node metadata for direct encrypted messages.
- **Integration identity:** Radarr, Sonarr, or another external app could have a separate age identity only if Rawrarr actually needs that app to decrypt or produce age-encrypted payloads independently. Do not create one merely because an integration is configured: today Rawrarr talks to Arr APIs, and app API keys/configuration are protected through Rawrarr's existing encrypted shared config and browser-to-node flow. Prefer a Rawrarr-managed per-integration key only if a concrete workflow requires isolation from the node process or other integrations.

For node-to-node messages, encrypt to the recipient node's public age recipient and authenticate that recipient through the already owner-approved node enrollment channel. Age encryption supplies confidentiality but not sender authentication; use the separately designed device signing/enrollment mechanism to bind recipient records, message type, instance, and sender. Do not accept a recipient learned only from an unauthenticated message or synchronized payload. A user identity and node identity may both be recipients for a deliberately shared object, but sharing must be explicit and revocation/rotation behavior must be defined.

Node identity creation must be atomic and survive restarts. On each subscriber startup, an absent identity is generated and stored once; an existing valid identity is reused. If an identity file exists but is unreadable or invalid, startup fails and leaves it untouched rather than overwrite it. If an identity is later lost, startup creates a new identity because no old file remains; that new key must not be treated as the previously enrolled identity. Before identity-bound messaging, replacement requires an explicit re-enrollment/rotation path that updates the authenticated public recipient and handles messages encrypted to the old key. Back up private node identities only through an explicitly designed encrypted recovery flow; never include them in ordinary shared-folder or node backups by default.

Automatic node identity generation and local persistence are implemented. Recipient enrollment, node-to-node encrypted messaging, and Arr application identities remain design decisions; the age-identity inventory, recipient directory schema, message envelope, and Arr integration threat model remain to be specified before implementation.

- Each Rawrarr device generates its own signing key pair during explicit enrollment. Derive the future stable Rawrarr `device_id` from a versioned fingerprint of the canonical public signing key (for example, a domain-separated SHA-256 digest), not from a hostname, display name, or role string. Specify encoding and algorithm agility before implementation.
- Keep three concepts separate: cryptographic `device_id`, editable human-readable `display_name`, and signed `role`/capabilities. A node record must state its function explicitly, such as `metadata` (user-facing name: `fossil`) or `storage` (user-facing name: `boneyard`). If a device performs multiple supported functions, represent that explicitly as a validated role/capability set instead of minting a different identity per function.
- The private signing key remains local to that node in protected node-local storage (for Docker, likely a dedicated local volume or mounted secret). It never enters `/shared`, `config.aged`, logs, backups in plaintext, or the relay/subscription database.
- The existing owner-approved coordinator enrollment is the trust bootstrap: the joining node proves possession of its candidate ML-DSA private key, and the owner approves that exact public key, derived device ID, and requested role/capabilities. The coordinator records the approved public key in its protected node registry so it can authenticate subsequent coordination requests. Do not trust a key merely because it appears in a pending request or in synchronized data.
- After approval, publish the approved device public key, algorithm/key-encoding version, device ID, display name, role/capabilities, and enrollment/revocation status in the age-encrypted shared config as the instance's replicated public-key registry. These are public verification records, not secrets. Every node verifies that the key derives the claimed ID and that its enrollment and role are authorized. Private signing keys remain node-local.
- The shared config cannot be the sole trust bootstrap for itself: a node needs an independently authenticated genesis trust anchor before accepting a config update or key registry signed by a key listed only in that update. Define how the initial trust anchor is pinned when creating the instance and how recovery works, then require authorized signatures over versioned config revisions that include registry changes. This prevents an untrusted writer from adding its own key and using it to bless its own update.
- Nodes may sign records they write beneath `/shared`, such as metadata sidecars or manifests. Each signed record should bind a format/version, `instance_id`, signer device ID, role/capabilities where relevant, record type, stable record identity/path, revision or generation, and exact payload bytes or ciphertext hash. Readers resolve the signer ID through the approved registry and reject unknown, revoked, mismatched, stale, or invalid signatures. Keep signatures detached or use a clearly versioned envelope so existing ciphertext formats can be migrated safely.
- Signatures cover canonical, versioned data including `instance_id`, `device_id`, role/capabilities, schema/revision, and the exact payload or ciphertext hash. Receivers validate that the signing public key derives the claimed `device_id`, plus the full enrollment chain, signature, authorized role/capabilities, revocation status, and revision before accepting a change.
- Under a device-root model, the first device key is also the instance root: its public key is placed in the initial age config, and it signs later device approvals. This is simple, but compromise or loss of that device key compromises or can strand the instance trust chain. Treat this as a deliberate choice, not an automatic property of being the first node. Under a separate-owner-root model, no device key is the root; the owner key approves the initial metadata/storage device and subsequent nodes. Roarlay may operate this authority on the owner's behalf if the owner explicitly entrusts its per-instance authority key to roarlay; the owner still approves each enrollment through the authenticated UI, and the key signs the approval record. A third option is a threshold or recovery authority, which reduces single-key dependence at added complexity. In every model, the second node is not trusted until the chosen authority signs/approves its exact enrollment record. Lost/replaced keys require revocation and recovery.
- Age encryption remains responsible for confidentiality. Device signatures prove authorship/integrity; they do not grant a user access to decrypt data and do not replace passkeys or Rawrarr sharing permissions.
- Tailscale identity remains transport identity. A node's overlay membership does not automatically authorize it to sign Rawrarr configuration.

## Compatibility and migration

Existing IDs such as `macbook-metadata` and `mac-mini-storage` are deployment identifiers used by current routes, configuration, and authentication scoping; they are not signing identities. Do not reinterpret them as key fingerprints or replace them in place. A future migration should add a cryptographic identity field and explicit role claim, maintain a reviewed mapping from legacy IDs during transition, and update relay targets, approved-node records, sessions, and shared configuration together. Display names such as “MacBook” and “Mac mini” remain descriptive metadata only.

A roarlay-held instance authority key is still per-instance trust, not a global Rawrarr publisher key. It can be generated during cluster setup and used only for that instance. Compromise must be scoped to that cluster, and software updates must not implicitly replace or rotate it.

## Root-key creation and enrollment experience

A candidate owner-root flow is:

1. Create or import the instance age identity and verify its backup first. The user may explicitly opt in to retaining only this age private ID in browser-local storage; the default/highest-security choice keeps it in active-tab memory and requires re-entry. Remove it on request or sign-out. Never put the root signing key in browser storage, IndexedDB, URLs, caches, or service-worker state.
2. Generate the per-instance ML-DSA root key in the owner-controlled client. Publish its public key and fingerprint as the instance trust anchor in the initial age-encrypted config.
3. Encrypt a backup of the root private key to that age identity. Show the owner the encrypted root-key backup with a clear instruction to copy it and save it somewhere they control. Explain that the age identity is required to unlock this backup and must have its own recoverable backup.
4. For later node enrollment, show the requested device name, public-key fingerprint, and role. Before approval, independently compare the candidate instance root fingerprint shown by the joining node with the owner's saved fingerprint; do not treat a fingerprint delivered only by Roarlay as independent verification. After passkey authentication and explicit approval, require the owner to enter the encrypted root-key backup for each approval. Decrypt it locally with the age identity, verify that its public key matches the independently pinned instance root fingerprint, sign the approval locally, and send only the signed approval to roarlay. Do not remember the encrypted backup or plaintext root key in browser storage; clear the backup input and discard plaintext root-key bytes after use or when the approval flow is cancelled or times out.
5. Before completing setup, require the owner to acknowledge a prominent recovery warning: **keep both the encrypted root-key backup and the age identity (including its own recovery backup). Losing either can prevent future device approvals and make the instance difficult or impossible to recover.** If the encrypted root backup is lost, the root cannot be restored; if the age identity is lost, the encrypted root backup cannot be decrypted. Recovery would require a separately designed and provisioned recovery authority; do not imply support until it exists. Root rotation and recovery need a separately authorized procedure.

Repeat this warning wherever the owner copies the backup, before approving a new device, and in recovery documentation. Do not bury it in generic help text. The user copies and pastes only ciphertext, never plaintext signing material. However, the client performing decryption and signing necessarily has the root key in memory temporarily; do not send it to roarlay, persist it unencrypted, put it in URLs/logs, or cache it beyond the approval action. The server may orchestrate the approval challenge and validate the resulting signature, but must not be trusted as the signer. The root public key/fingerprint pairing and initial trust bootstrap need integrity protection; a config must not silently replace its own trust anchor.

## Global software signing versus instance trust

A global Rawrarr publisher signing key could authenticate official releases, update manifests, or shipped trust-policy metadata. It should not by itself authorize a subscriber's devices, sign that subscriber's `/shared` records, or control the instance enrollment root. Those are separate trust domains: Rawrarr publisher identity answers “was this artifact published by Rawrarr?”, while the instance trust authority answers “did this owner authorize this node and its role?”. If a global key is considered, define offline custody, rotation, compromise recovery, and narrowly scoped signed artifacts. Never embed its private key in node images or runtime containers.

## Cryptographic choice

**Initial candidate: ML-DSA (NIST FIPS 204).** Evaluate it first for per-device signing keys, signatures, and public-key-derived device IDs. Keep the algorithm identifier and public-key encoding versioned in identity records so a later algorithm migration does not require pretending old IDs are ML-DSA identities. ML-DSA is a post-quantum signature scheme; its use here remains proposed until safe Rust library support, interoperability, canonical message encoding, and operational key handling are reviewed.

Tephramesh currently uses per-device P-256 ECDSA signing keys for its signed configuration envelopes and enrollment approvals; reuse the architectural separation—local private key, synchronized public trust records, explicit enrollment, signed revisions—not the algorithm by default. P-256 may be considered as a separately specified hybrid component if transition interoperability warrants it. Any hybrid profile must define whether both signatures are required and prevent silent downgrade to classical-only verification. Also evaluate key rotation, long-term verification support, public-key/signature sizes, and post-compromise recovery.

## Decisions and tests before implementation

- Choose which `/shared` record classes require signatures (config revisions, manifests, metadata sidecars, or all of them), how signatures are stored, and whether metadata signatures cover ciphertext bytes, plaintext canonical content, or both. Avoid signing unstable Syncthing transport state.
- Specify root genesis and independent fingerprint distribution/pinning, including how already-deployed nodes acquire their first pin without replacing existing node IDs or bearer credentials. Define recovery, multi-owner approval, device replacement, revocation, rollback detection, and how disconnected devices learn revocations.
- Decide whether any global publisher key is needed for software/update authenticity, separately from per-instance device authorization.
- Define role/capability vocabulary, whether functions are singular or multi-valued, and which authority can approve role changes independently of key identity.
- Select a canonical serialization and implement the initial ML-DSA profile with safe Rust libraries; keep `unsafe_code` forbidden in Rawrarr's own crate. If a hybrid is later justified, specify its required verification rule and downgrade resistance.
- Test tampered bytes, unknown signers, revoked keys, stale revisions, wrong `instance_id`, key rotation, restore from backup, and offline peers.
- Prove private signing keys never enter Syncthing, relay APIs, logs, process arguments, or shared backups. The age-encrypted shared config may contain approved public keys and signed public records, never private signing keys. Encrypted backup archives may contain signed public records but never local private keys.

## Reference

The design review used Tephramesh's `readme/SIGNING.md` and `src/config-signing.ts` as an example of enrollment roots, device-bound keys, signed revisions, and revocation. Rawrarr has different runtime, storage, and post-quantum requirements, so this is a pattern reference rather than a compatible protocol.
