# Rawrarr data domains

Rawrarr uses stable container paths to describe where each kind of data belongs. The paths are the same on every node; a node only mounts the domains it can serve. `/local` holds node-local persistent state. `/evt` is the event-data root: `/evt/fossil` is the encrypted metadata/config domain for authenticated RPC replication, and `/evt/boneyard` is the Syncthing domain for explicitly shared large files and media folders. The application can use these paths, but generated and checked-in Compose default to legacy write mode for mixed-version rollout. Only explicitly owner-approved nodes may join either replication domain; enrollment and network reachability alone do not grant access.

The event tree separates metadata from media/file replication. Event write mode stores encrypted configuration and metadata under `/evt/fossil` and exchanges signed metadata revisions and ciphertext over authenticated peer RPC. `/evt/boneyard` contains files deliberately synchronized by Syncthing, including selected media folders. Both the Rawrarr container and its Syncthing companion mount the same selected host folder at `/evt/boneyard`; Syncthing's folder must use that container path. During mixed-version rollout, a separate legacy Syncthing folder at `/shared` keeps default legacy writers compatible. Never add `/evt/fossil` to Syncthing. Neither event domain includes node-local `/local` or coordinator PostgreSQL.

| Domain | Container path | Present on | Persistence and sync | Contents |
|---|---|---|---|---|
| Media source | `/media` | Storage nodes that can read media | Host media mount, read-only in Rawrarr; never copied automatically | Original movie, TV, music, book, subtitle, and other library files |
| Metadata | `/evt/fossil/metadata` | Authorized subscribers | Signed fixed-path RPC in event write mode; compatibility copy retains old sources and conflicts | Age-encrypted app metadata and artwork |
| App configuration data | `/evt/fossil/config.aged` | Authorized subscribers | Signed config RPC/mirror in event write mode; legacy `/shared/config.aged` remains supported | Encrypted managed-app settings such as URLs, API keys, and preferences |
| Syncthing files | `/evt/boneyard` | Approved Syncthing peers | Same explicit `RAWARR_BONEYARD_DATA_PATH` host bind in app and Syncthing Compose; separate from transitional `/shared` compatibility folder | Selected media folders and other large files |
| Local operational state | `/local` | Each node | Node-local persistent volume; never synced | Device ID, revision journals, identities, credentials, and optional development-only config mirror |
| Valkey cache | In-memory service | One subscriber Compose project | Disposable, non-persistent cache; no volume and no shared/event mount | Exact encrypted config mirror and optional artwork cache |
| Database | PostgreSQL data volume | Coordinator | Node-local database volume; never put its live datadir in Syncthing | Current passkey/authentication database and local projections |
| Event-data backups | Configured node-local destination | One designated subscriber node | Stored outside `/evt`, never replicated; destination is recorded in encrypted configuration | Verified snapshots of event data only; excludes `/local`, database, and source `/media` |

## Placement rules

- The coordinator's environment-owner record stores only the authenticated account reference, pinned personal age public recipient, source fossil ID, and provisioning timestamp in PostgreSQL. It is separate from the ML-DSA instance-signing root. The private user age identity stays on a subscriber or owner recovery device; group/device recipients are not substitutes. See the [backup owner-recipient runbook](../runbooks/2026-11-03-environment-owner-backup-recipient.md).

- The coordinator owns the user-facing web/auth stack and PostgreSQL. Storage and shard nodes can hold authorized shared ciphertext without those services; `/evt/fossil` is the target metadata domain.
- Only storage capability mounts local source media read-only under `/media`. A selected copy may be deliberately published under `/evt/boneyard` for Syncthing replication after owner approval; it is not an automatic mirror. A coordinator can optionally also have storage capability. A shard has no media mount; multi-library/cross-node catalog behavior remains planned.
- `/evt/fossil` and `/evt/boneyard` are separate replication domains. Migration from `/shared` retains the old source and copies only missing files; conflicting targets are preserved. Keep `RAWARR_EVT_WRITE_MODE=legacy` until every authorized peer runs the RPC-capable release and the service-topology rollout checks pass.
- Valkey is a disposable node-local cache. It has persistence disabled and no volume mount; the encrypted config file and signed revision journal on the fossil node remain authoritative. Do not add `/local`, `/evt`, or `/shared` as a Valkey data volume.
- `docker-compose.yml`, `docker-compose.metadata.yml`, `docker-compose.storage.yml`, and generated subscriber Compose bind the selected host boneyard directory to `/evt/boneyard`. `docker-compose.syncthing.yml` must use the same `RAWARR_BONEYARD_DATA_PATH`; its boneyard folder is configured at `/evt/boneyard`. Keep that host directory disjoint from the legacy `RAWARR_SHARED_DATA_PATH`; do not point the boneyard folder at `/evt`, `/evt/fossil`, or `/shared`.
- While writers default to legacy mode, Syncthing also needs the separate compatibility bind at `/shared`. The local bootstrap preserves the known peer-free `/shared` folder and adds `/evt/boneyard`, after verifying both host binds. Peer-connected deployments need a coordinated folder migration; do not broadly rewrite their existing configuration. Once all nodes use event mode and legacy data is verified, retire the `/shared` Syncthing folder in a separate migration. See the [config peer-repair protocol](metadata-peer-repair-protocol.md).
- The preparatory `app-identities.aged` file contains group-encrypted Radarr/Sonarr identity material; it is ciphertext only, and older binaries ignore it. Do not edit it directly or have multiple nodes initialize/update it concurrently. Keep `config.aged` and metadata on the existing group recipient until every reader, writer, and browser path has been upgraded and old writers are fenced; app-key metadata migration is not active.
- Metadata files use `.aged`; names and directory structure should avoid leaking media titles or absolute host paths. The current library sidecar filename is a stable hash, and the relative media path stays inside ciphertext. The `/evt/boneyard` category is for large published files and does not imply those files are age-encrypted.
- Group metadata first by media type, then by content kind. Movie, TV, music, and book records are stored beneath `/evt/fossil/metadata` in event mode; generic inventory sidecars follow the same encrypted metadata domain. Legacy-mode writers continue to use `/shared` until the coordinated writer cutover.
- Radarr movie records use HMAC-SHA-256 filenames under `movies/text/`; poster bytes use separate domain-separated HMAC names under `movies/artwork/`. The 256-bit OS-random `metadata_filename_key` is held in age-encrypted `config.aged`; do not rotate it after data is written. Schema version 2 stores the full Radarr movie API record, including its text and ratings fields and available movie-file details, while removing node-local paths and byte-size values. Metadata-node refreshes this record on library reads and in its six-hour backfill. Movie artwork remains in its separate encrypted folder. Legacy numeric files are copied byte-for-byte to HMAC paths, verified, and removed; readers support numeric names during transition.
- Sonarr series records and posters use separate TVDB-domain-separated HMAC names under `tv/text/` and `tv/artwork/`. Schema version 2 stores the full series API record plus each series' episode records, including text and available file details; node-local paths and byte-size values are removed. The metadata-node backfill refreshes records sequentially after connection and every six hours. Storage-node observations remain separate under `library/text/`, even when they describe the same media files.
- When a Radarr connection and unlocked age vault are available, Rawrarr asks Radarr for a native manual backup every six hours and stores only the latest archive under the active metadata directory at `radarr/recovery.zip.aged` (legacy `/shared/in/metadata` or event `/evt/fossil/metadata`). The archive includes Radarr configuration and database state, which may contain API keys and integration credentials, so it is age-encrypted before filesystem storage and RPC transfer. It must never enter Syncthing's boneyard folder. Optional Radarr UI credentials used to fetch login-protected backups are stored only in the age-encrypted config, never in the node-local plaintext Radarr mirror. Users deploy Radarr themselves on a chosen node and run `scripts/restore_radarr.py` to decrypt locally and upload the archive. The restore does not copy or modify media files; target root-folder paths must match the paths in the backup or be repaired after restore.
- Do not write media bytes, private age identities, plaintext configuration, sessions, challenges, or a live PostgreSQL datadir under `/evt/fossil` or `/evt/boneyard`. The local development service may keep `radarr-config.json` under `/local` with mode `0600`; production disables this copy. Keep private identities and credentials in `/local`, and replicate only encrypted metadata and settings through their approved transport.
- User passkeys and browser sessions belong to the coordinator; storage-only and shard nodes use device identity instead. Portable user/passkey records and secure passkey-first bootstrap are future work; they are not copied merely because a node participates in Syncthing. Portable records for future multiple-coordinator use remain undecided and are not required for this deployment.

## Container mapping

The MacBook's current node-local media replica root is `~/Library/Application Support/rawrarr/media.ev/`, with its synchronized music under `music/`. A separate `~/Library/Application Support/rawrarr/media/` tree holds empty planned receive folders matching the Mac mini's observed top-level media kinds: `audiobooks.ev/`, `books.ev/`, `comics.ev/`, `images.ev/`, `movies.ev/`, `music.ev/`, `podcasts.ev/`, `roms.ev/`, and `tv.ev/`. The `.ev` suffix means “eventually.” These category folders are placeholders, not active Syncthing shares or enrolled nodes. A future movies-only node could mount `media/movies.ev` as its receive destination, with an explicit movie source, owner approval, a distinct folder ID, a receive-only destination, and content verification. Apply the same scoping to other categories; the existence of a placeholder never grants access. Container paths may remain `/media` regardless of the host folder name.

The target Docker layout mounts `/local` for private state and `/evt` for event data. Store RPC metadata under `/evt/fossil`; configure its Syncthing folder for `/evt/boneyard`. During mixed-version rollout, preserve the separate `/shared` compatibility folder for legacy writers. Compressed operational logs must remain local unless explicitly classified and authorized for replication. `RAWARR_LIBRARY_PATH` identifies the media root and should be `/media` in a storage container.

Compose persists `/local` and `/evt` separately. Keep both outside the source checkout and never place private age identities or PostgreSQL data in `/evt`. Existing host `shared-data` directories remain mounted as compatibility storage until an explicit migration is completed. Set `RAWARR_BONEYARD_DATA_PATH` to the same intentionally selected host directory in both the Rawrarr and Syncthing Compose invocations; do not use the entire legacy shared-data tree.

This registry defines placement and sync boundaries. It does not imply that a web node can remotely read a storage node's `/media` tree or that a metadata reader, catalog projection, or remote scan-command channel already exists. The current prototype still configures one local root through `RAWARR_LIBRARY_PATH`; multi-library and cross-node aggregation are planned behavior.

The planned [local backup feature](local-backups.md) stores a target device ID and its local destination in the encrypted event metadata. Only that node writes backup archives, and the destination must remain outside `/evt` so backups do not sync back into the instance.

Movie text metadata also caches `qualityProfileId` and `qualityProfile.name`. Movies reads these encrypted shared values first, resolves missing names in one Radarr quality-profile request, and merges updates without replacing other metadata. A changed assigned ID invalidates the cached name. Reading existing ciphertext requires the unlocked subscriber vault; unreadable metadata is not overwritten.
