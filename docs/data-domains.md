# Rawrarr data domains

Rawrarr uses stable container paths to describe where each kind of data belongs. The paths are the same on every node; a node only mounts the domains it can serve. `/shared` remains the root of the Syncthing folder. `/metadata` is an in-container alias for `/shared/metadata`, not a second sync folder. Only explicitly owner-approved nodes may be configured as Syncthing peers or receive this shared folder; node enrollment, Tailscale membership, or network reachability alone does not grant shared-data access.

The target shared-tree layout separates `/shared/in` for app data shared between nodes (such as Radarr metadata exchanged between fossils) from `/shared/out` for larger files published by a node (such as selected media collections). Both are ordinary subdirectories in the configured Syncthing folder and use Syncthing replication between approved peers. Portable app data should synchronize **eventually**, including after offline periods, but that is a design goal and does not make every database row or setting shared. The current deployment still uses `/shared/metadata`; moving it under `/shared/in` requires a future migration. Node-local database and `/data` contents remain local.

| Domain | Container path | Present on | Persistence and sync | Contents |
|---|---|---|---|---|
| Media source | `/media` | Storage nodes that can read media | Host media mount, read-only in Rawrarr; never copied automatically | Original movie, TV, music, book, subtitle, and other library files |
| Metadata | `/metadata` | Every node | Alias of `/shared/metadata`; age-encrypted files sync as part of the shared folder | Grouped media metadata and artwork, generic scan sidecars, and the latest Radarr recovery archive at `radarr/recovery.zip.aged` |
| Shared app state | `/shared` | Every node | Currently Syncthing replicated; planned RPC/Merkle-only replication for `config.aged`, with a local Valkey ciphertext mirror | Encrypted `config.aged`, public `age-recipient`, and the metadata domain |
| Incoming/shared app data (target layout) | `/shared/in` | Approved peers | Intended Syncthing subtree; migration from current `/shared/metadata` is not implemented | Portable app records and age-encrypted metadata exchanged between fossils |
| Published large files (target layout) | `/shared/out` | Approved peers selected for a content set | Intended Syncthing subtree; explicit owner-approved sharing | Large file collections such as selected media; file-at-rest encryption is separate from Syncthing transport encryption |
| Local operational state | `/data` | Each node | Node-local persistent volume; never synced | Device ID, local runtime state, and an optional owner-only plaintext Radarr config mirror in local development |
| Database | PostgreSQL data volume | Coordinator | Node-local database volume; never put its live datadir in Syncthing | Current passkey/authentication database and local projections |
| Shared-folder backups | Configured node-local destination | One designated subscriber node | Stored outside `/shared`, never Syncthing-replicated; destination device/path is recorded in age-encrypted `config.aged` | Verified snapshots of the shared Rawrarr folder only; excludes node-local database and `/media` |

## Placement rules

- The coordinator owns the user-facing web/auth stack and PostgreSQL. Storage and shard nodes can hold authorized shared ciphertext without those services; `/metadata` remains an alias inside `/shared`.
- Only storage capability mounts local source media read-only under `/media`. A selected copy may be deliberately published under `/shared/out` for Syncthing replication after owner approval; it is not an automatic mirror. A coordinator can optionally also have storage capability. A shard has no media mount; multi-library/cross-node catalog behavior remains planned.
- `/metadata` is a classification and access path, not a separate Syncthing folder. Current metadata remains physically under `/shared/metadata`; the target layout places it under `/shared/in/metadata` after a separately planned migration. Both remain part of the same configured `/shared` Syncthing folder.
- Current deployed behavior still syncs `/shared/config.aged` through Syncthing. The planned config peer-repair phase will exclude only root `/config.aged` from each node's local Syncthing folder and transfer it through authenticated RPC/Merkle; `.stignore` must be configured and verified independently on both nodes. App metadata and artwork under `/shared/metadata` remain in Syncthing. See the [config peer-repair protocol](metadata-peer-repair-protocol.md).
- Metadata files use `.aged`; names and directory structure should avoid leaking media titles or absolute host paths. The current library sidecar filename is a stable hash, and the relative media path stays inside ciphertext. The `/shared/out` category is for large published files and does not imply those files are age-encrypted.
- Group metadata first by media type, then by content kind. Movie text records use `/metadata/movies/text/`, movie artwork uses `/metadata/movies/artwork/`, and future TV, music, and book records follow the same `<type>/{text,artwork}/` layout. Generic inventory sidecars use `/metadata/library/text/` until they can be assigned a media type. All files remain age-encrypted and sync through the same `/shared` folder.
- Radarr movie records use HMAC-SHA-256 filenames under `movies/text/`; poster bytes use separate domain-separated HMAC names under `movies/artwork/`. The 256-bit OS-random `metadata_filename_key` is held in age-encrypted `config.aged`; do not rotate it after data is written. Schema version 2 stores the full Radarr movie API record, including its text and ratings fields and available movie-file details, while removing node-local paths and byte-size values. Metadata-node refreshes this record on library reads and in its six-hour backfill. Movie artwork remains in its separate encrypted folder. Legacy numeric files are copied byte-for-byte to HMAC paths, verified, and removed; readers support numeric names during transition.
- Sonarr series records and posters use separate TVDB-domain-separated HMAC names under `tv/text/` and `tv/artwork/`. Schema version 2 stores the full series API record plus each series' episode records, including text and available file details; node-local paths and byte-size values are removed. The metadata-node backfill refreshes records sequentially after connection and every six hours. Storage-node observations remain separate under `library/text/`, even when they describe the same media files.
- When a Radarr connection and unlocked age vault are available, Rawrarr asks Radarr for a native manual backup every six hours and stores only the latest archive at `/shared/metadata/radarr/recovery.zip.aged`. The archive includes Radarr configuration and database state, which may contain API keys and integration credentials, so it is age-encrypted before entering Syncthing. Optional Radarr UI credentials used to fetch login-protected backups are stored only in the age-encrypted `config.aged`, never in the node-local plaintext Radarr mirror. Users deploy Radarr themselves on a chosen node and run `scripts/restore_radarr.py` to decrypt locally and upload the archive. The restore does not copy or modify media files; target root-folder paths must match the paths in the backup or be repaired after restore.
- Do not write media bytes, private age identities, plaintext configuration, sessions, challenges, or a live PostgreSQL datadir under `/shared` or `/metadata`. The local development Compose service may keep `radarr-config.json` under `/data` with mode `0600`; production must disable this copy and retain only encrypted `config.aged` under `/shared`.
- User passkeys and browser sessions belong to the coordinator; storage-only and shard nodes use device identity instead. Portable user/passkey records and secure passkey-first bootstrap are future work; they are not copied merely because a node participates in Syncthing. Portable records for future multiple-coordinator use remain undecided and are not required for this deployment.

## Container mapping

The MacBook's current node-local media replica root is `~/Library/Application Support/rawrarr/media.ev/`, with its synchronized music under `music/`. A separate `~/Library/Application Support/rawrarr/media/` tree holds empty planned receive folders matching the Mac mini's observed top-level media kinds: `audiobooks.ev/`, `books.ev/`, `comics.ev/`, `images.ev/`, `movies.ev/`, `music.ev/`, `podcasts.ev/`, `roms.ev/`, and `tv.ev/`. The `.ev` suffix means “eventually.” These category folders are placeholders, not active Syncthing shares or enrolled nodes. A future movies-only node could mount `media/movies.ev` as its receive destination, with an explicit movie source, owner approval, a distinct folder ID, a receive-only destination, and content verification. Apply the same scoping to other categories; the existence of a placeholder never grants access. Container paths may remain `/media` regardless of the host folder name.

The Docker image sets `RAWARR_METADATA_DIR=/metadata` and makes `/metadata` a symlink to `/shared/metadata`. Native runs can omit that variable; Rawrarr then uses `$RAWARR_SHARED_DATA_DIR/metadata`. Keep an override inside the shared folder if setting it manually. Compressed operational logs are stored under `$RAWARR_SHARED_DATA_DIR/logs/<device-id>/` and synced as application data. `RAWARR_LIBRARY_PATH` identifies the media root and should be `/media` in a storage container.

The local Compose example bind-mounts `$HOME/Library/Application Support/rawrarr/shared-data` at `/shared` by default so the shared data is persistent and directly accessible in Finder. Override the host directory with `RAWARR_SHARED_DATA_PATH` when needed. Keep this directory outside the source checkout and never place private age identities or PostgreSQL data in it.

This registry defines placement and sync boundaries. It does not imply that a web node can remotely read a storage node's `/media` tree or that a metadata reader, catalog projection, or remote scan-command channel already exists. The current prototype still configures one local root through `RAWARR_LIBRARY_PATH`; multi-library and cross-node aggregation are planned behavior.

The planned [local backup feature](local-backups.md) stores a target device ID and its local destination in the shared encrypted configuration. Only that node writes backup archives, and the destination must remain outside `/shared` so backups do not sync back into the instance.

Movie text metadata also caches `qualityProfileId` and `qualityProfile.name`. Movies reads these encrypted shared values first, resolves missing names in one Radarr quality-profile request, and merges updates without replacing other metadata. A changed assigned ID invalidates the cached name. Reading existing ciphertext requires the unlocked subscriber vault; unreadable metadata is not overwritten.
