# Coordinator analytics

Rawrarr can optionally send one anonymous page-view event from the coordinator landing/workspace page to a self-hosted Umami instance. Analytics is off unless both `RAWARR_ANALYTICS_UPSTREAM` and `RAWARR_ANALYTICS_SITE_ID` are configured. It never tracks subscriber pages, APIs, health checks, node relays, or user actions.

The integration disables Umami's automatic tracking and submits only a fixed `/coordinator` page label and title. It does not send the browser URL, query string, referrer, account/device/node identifiers, library data, or event properties. The site ID must contain only letters, digits, hyphens, or underscores. The server proxy only allows `http://umami:3000` and the Umami tracker and event routes. Invalid or incomplete settings leave tracking disabled. The coordinator forwards the client IP and browser user-agent to Umami so it can calculate visitor metrics; Umami uses these to derive anonymous session metrics. Self-hosting controls where this data is stored but does not mean no visitor data is processed. Review Umami's [metric definitions](https://docs.umami.is/docs/metric-definitions).

## Deployment

Merge `docker-compose.analytics.yml` into the existing coordinator Compose project on each host. Set `RAWARR_ANALYTICS_NETWORK` to that coordinator project's private Docker network (the current do3 networks are `rawrarr-internal-do3-control` and `rawrarr-roarlay-prod-control`). Umami joins that private network, while its PostgreSQL port is not published. The Umami web service binds only to host loopback port 7300 for administration. The coordinator proxies the tracker and event endpoints at its existing HTTPS origin under `/analytics`; no new public hostname, DNS record, Caddy route, or external tracker connection is needed. Use a separate Umami website/site ID for each environment, and preserve each project's separate `umami-postgres-data` volume. The analytics database is not Rawrarr PostgreSQL and contains no Rawrarr application records. The coordinator proxy permits only `GET /analytics/script.js` and `POST /analytics/api/send`, with bounded bodies and responses.

Use an SSH local port forward to access the dashboard at `http://127.0.0.1:7300` (or restrict access to that loopback listener on the host). Public users cannot reach the dashboard through the coordinator proxy. Do not expose PostgreSQL. Set `RAWARR_ANALYTICS_UPSTREAM=http://umami:3000` and `RAWARR_ANALYTICS_SITE_ID` to that environment's Umami website ID. Leave either empty to disable tracking.

Create a strong independent DB password, an application secret, and a 64-character hex 2FA encryption key in the host's protected environment file. Keep that file out of Git and `/shared`. Self-hosted Umami does not expire data automatically, so the overlay runs a PostgreSQL maintenance container that deletes visitor/event records older than 90 days once per day. It uses the Umami `3.4.1` PostgreSQL schema and a repeatable transaction; keep it aligned when upgrading Umami. Back up the Umami database separately and test restore before upgrades. The Umami application image is pinned to `3.4.1`; review upstream security releases before changing the tag. Upgrade the analytics service independently from Rawrarr.

For both internal and public coordinator deployment files, pass `RAWARR_ANALYTICS_UPSTREAM` and `RAWARR_ANALYTICS_SITE_ID` to roarlay. Use separate site IDs and database volumes so internal testing traffic does not mix with public usage. Start `umami-postgres`, `umami`, and `umami-retention`; create an administrator, enable 2FA, create the environment-specific website, then enable the coordinator settings. Verify the browser loads `/analytics/script.js`, posts only the fixed `/coordinator` pageview to `/analytics/api/send`, and the event appears in that environment's dashboard. To roll back, clear either coordinator setting and recreate roarlay; the Umami service, retention service, and its volume can remain running. Deleting the Umami volume permanently deletes analytics history. The 90-day policy permanently deletes older event/session data; restore an Umami database backup to recover purged history, or stop `umami-retention` before a planned maintenance window.

This adds a separate analytics data domain but changes no Rawrarr persistent data, schema, node protocol, or synchronized `/shared` content. Existing deployments adopt it by adding the analytics Compose overlay and the two optional coordinator environment variables; no migration is required.
