# Device and scanner architecture

> Current user-facing names: **roarlay** (coordinator), **fossil** (metadata), and **boneyard** (storage). Only boneyard reads local media. The coordinator displays a selected node UI through a configured relay; `localhost:7297` remains available for direct local access. See [implemented deployment and Mac mini setup](container-deployment.md). Manual node approval and single-account node ownership are implemented; multi-account invitations and dynamic node channels remain planned.

The accepted container roles are `coordinator`, `storage`, and `metadata`; their user-facing names are roarlay, boneyard, and fossil respectively. The coordinator runs user authentication, PostgreSQL, account ownership, and node coordination; storage reads its local media mount; metadata serves Radarr and shared application data. Coordinator and subscriber capabilities stay separate. The MacBook runs coordinator and fossil containers; the Mac mini is a boneyard node. The operator service is separate. See [node types](node-types.md) and [coordinator linking](coordinator-linking-plan.md).

A **dino** is a user-deployed Rawrarr node, not a new runtime role. It may run fossil metadata services and at most one media role: boneyard for local media storage or tarpit for a future encrypted Syncthing destination. Boneyard and tarpit are mutually exclusive on one dino; fossil may be combined with either. Tarpit remains planned and unimplemented; see [node types](node-types.md) for terminology.

## Current prototype boundary

The first installation bootstraps one coordinator, its PostgreSQL database, and an initial fossil node with a protected pre-approved node credential. The first passkey registration creates the coordinator instance's owner account. The account and passkey session live only in coordinator PostgreSQL; the initial fossil provides the temporary web UI and proxies authentication to the coordinator. A successful passkey registration/sign-in sends the browser to age setup when the encrypted config is still locked. Creating an ID happens in the browser-facing setup flow: the server returns the new identity for client-side copying, but the app does not save it in PostgreSQL, `/shared`, logs, or a service-node component. A generated identity opens the copy pop-up; the user copies it and confirms the copy, enabling Continue. Selecting Continue unlocks the vault and navigates to the dashboard. The three-character check is temporarily disabled. The dialog has no Close action. Pasted identities unlock directly through **Unlock vault**, without copy acknowledgement. Both flows offer explicit local persistence: **Keep this ID on this device** writes an owner-only `/data/age-identity` file in local Compose. The subscriber fossil process holds the identity while unlocked and can reload a remembered identity on startup; passkey sign-in remains required.

The unlocked configuration is saved as age ciphertext in `/shared/config.aged`. Local Compose can also maintain an owner-only plaintext Radarr settings mirror in node-local `/data/radarr-config.json` so local tools can use the configured integration without passkey or age handling; this mirror is disabled and removed in production. Settings saved through Rawrarr update both files, and unlocking the shared config refreshes the local mirror from the ciphertext. Dashboard snapshots are sent over the web process's `/api/events` server-sent events route. The `/health` route returns an HTML web-process status page used by the container health check; it does not establish database or integration health. Current local Compose is a development/self-hosting shape; it does not provision subscriber instances or run the future operator service, claim protocol, Headscale automation, or public relay. Public-domain/proxy behavior for long-lived dashboard event streams still requires end-to-end deployment verification.

This local prototype boundary is distinct from the intended deployment roles below. The Mac mini boneyard deployment and coordinator-hosted workspace are implemented; multi-account invitations, a separate operator service, and a cross-node catalog remain planned.

## Coordinator-hosted node workspace

At `https://rawrarr.risk-mermaid.ts.net/`, the owner signs in with a passkey registered for that HTTPS origin, reviews pending node approvals, and opens a selected registered fossil or boneyard node's Rawrarr pages. Existing `localhost` passkeys do not automatically work at this hostname; the coordinator credential is explicitly linked to the existing account. The coordinator lists only owner-owned nodes and uses `RAWARR_NODE_RELAY_TARGETS` to map approved node IDs to trusted HTTP(S) base URLs. Its default local route points to the MacBook fossil container on the shared Docker network. A boneyard node needs its own configured route that the coordinator can reach; the Mac mini deployment does not yet expose that route. See the [workspace and relay implementation runbook](../runbooks/2026-10-18-coordinator-node-workspace.md) and [earlier relay plan](../runbooks/2026-10-18-coordinator-node-workspace-relay-plan.md).

The current self-hosted relay is a trusted application intermediary: it terminates the browser connection and can see proxied node UI/API plaintext. It creates a separate owner session scoped to the selected node and never forwards the coordinator cookie or node bearer token to that node. It must remain excluded from media mounts, private age identities, and node-local data. The configured direct route is the current implementation; authenticated persistent outbound channels are future work for nodes that cannot be reached at a configured address. This is separate from a future hosted blind relay, which must preserve end-to-end browser-to-node encryption.

The MacBook fossil node also has an optional direct Tailscale path for the coordinator workspace's encrypted library and ciphertext export requests. Tailscale Serve maps a dedicated path to a loopback-only listener that exposes only those allowlisted APIs; the coordinator issues a short-lived, node-scoped HttpOnly cookie after owner and Origin checks. The browser automatically probes that path, shows the active route, and falls back to the coordinator relay when direct access fails. Other node UI/API routes remain unavailable through the direct listener. Same-LAN routing and direct paths for additional nodes are not implemented.

## Ownership boundaries

- **Roarlay (coordinator):** subscriber primary UI/API, passkeys, PostgreSQL, account ownership, catalog, enrollment, and task coordination. It presents the connected fossil and boneyard nodes as one workspace.
- **Fossil (metadata):** serves the app and Radarr integrations, participates in `/shared`, and does not read `/media`.
- **Boneyard (storage):** reads local media beneath `/media`, publishes encrypted inventory/metadata, and authenticates outbound to the coordinator with its own device identity. No local PostgreSQL, user passkeys, or private age identity is required for encryption-only scanning. Mixed and category-specific libraries may contribute to the coordinator catalog; multi-library aggregation remains planned.

The owner can start a storage scan from Devices and stop it through the protected `POST /api/library/scan/cancel` route. Cancellation is cooperative: the current file's hash, ffprobe, and encrypted sidecar write finish safely, then the worker stops before starting another file. The status route reports `cancelled` and the completed-file count; daily scans do not overlap an active scan.
- **Service node:** operator-owned SwarmSail/Headscale, account/subscription, and future blind-relay role. It coordinates tailnets but does not join or decrypt a subscriber's `/shared` data and does not proxy media.
- **Optional Tailscale sidecar:** joins the user's tailnet for private Rawrarr web/API and control/application-data traffic, plus optional Service advertisement. It has a node-local identity and state; Rawrarr can still start and be reached locally without it. Rawrarr never uses Tailscale to transfer media files or streams; `/media` remains on its boneyard node.
- **Download agent (future):** runs where its configured client or destination is available and receives narrowly scoped work from the coordinator.

## Data domains

Rawrarr's canonical path and synchronization rules are listed in [data domains](data-domains.md). `/media` is a boneyard-local read-only mount; `/metadata` is the metadata domain available on every node and aliases `/shared/metadata`; `/shared` is the Syncthing root, including compressed operational logs under `/shared/logs`; `/data` and PostgreSQL storage remain node-local. A web node may omit `/media` entirely.

## Local and shared app data

Node-local `/data` holds device identity and operational state. PostgreSQL has its own coordinator-local volume for user authentication and future catalog/control records. Storage progress or queues can use local files or a lightweight store if needed. Never sync a live PostgreSQL datadir.

The separate Syncthing folder currently holds shared application records, including age-encrypted configuration (`config.aged`) and encrypted metadata/artwork (`.aged`). Configure a new production node as a Syncthing peer and share this folder only after the owner explicitly approves the node. Enrollment, Tailscale membership, and network reachability do not authorize synchronization. The metadata path `/metadata` points into that folder at `/shared/metadata`; it does not introduce a second sync root. It also contains the public age recipient so a scanner can encrypt new records without receiving a private identity; the recipient is public key material, not a secret. Rawrarr may keep a local PostgreSQL projection/cache of those records, but it is not the shared source of truth. Ciphertext and its directories must be readable/traversable by Syncthing; private age identities and plaintext config never belong in the share. See the [roadmap](../ROADMAP.md) for device enrollment and catalog synchronization work.

The first node is bootstrapped with roarlay and its initial fossil together; its first passkey creates the one owner account for that coordinator instance. Later nodes send only node metadata and proof of their node-local token. The coordinator assigns a pending request to its sole account and exposes it only to that account's signed-in owner for approval. A joining node does not name or choose a user. The current implementation rejects enrollment if the coordinator has zero or multiple accounts; supporting multiple accounts requires a signed-in owner to create a short-lived invitation and deliver it to the joining node. Boneyard-only nodes do not need copies of user passkeys or browser sessions. The coordinator-hosted dashboard is the primary entry point; the MacBook fossil UI remains directly available on localhost for local diagnosis.


Rawrarr's wider direction is a unified media automation system with a Prowlarr-class discovery role plus library management and fulfillment. See [product direction](product-direction.md) for the intended design and the [roadmap](../ROADMAP.md) for implementation status.

In the planned multi-node model, a device may publish multiple named libraries, and each library may contain one or more media kinds. A mixed root can therefore be scanned as one library, while separate movie, television, or music roots can be configured as distinct libraries on that device. The same category may also appear on multiple devices. Their host paths stay local to their device. The web catalog identifies files by device, library, and relative path; it never needs the device's absolute mount path. The workspace combines library inventories across the instance without making one node mount another node's media. If a device goes offline, its last inventory remains visible and is marked stale.

## Device record

A device record needs a stable ID, display name, role/capabilities, connection type, software version, last-seen time, and its library summaries. Libraries need stable IDs and display names; their scan inventory determines media kinds, rather than assigning a whole physical device to only one kind. Scan snapshots carry relative file path, media kind, size, optional modification time, and optional content fingerprint. A future implementation should report removals as tombstones or full-snapshot generations so stale entries can be reconciled safely.

## Shared instance identity

`instance_id` identifies one logical Rawrarr shared folder/namespace. Every node that synchronizes that folder has the same `instance_id`; each node still has its own unique `device_id`. A device may participate in multiple instances, and an instance may have multiple devices. The ID represents the shared folder identity, not its host path, a person, a running process/container, or a physical device. Moving the folder or changing sync providers must not change it.

Keep the Rawrarr `instance_id` independent from the transport's folder identifier. For Syncthing, map the Rawrarr instance to a Syncthing folder ID; a future transport can map the same Rawrarr instance to its own identifier. The shared instance manifest records the stable `instance_id` and is replicated with the shared state. Creating an independent copy/fork should mint a new ID; restoring or adding a node to the same shared instance preserves the existing ID.

An `instance_id` is an identifier, not a secret or authorization token. Access still requires an authenticated device membership and a valid user/share grant. The public relay may use the `instance_id` to find participating device IDs and live routes, but knowing it must never permit a connection or reveal instance contents.

## Pairing and transport

The agent should initiate outbound HTTPS requests to the web service; the web service does not open inbound connections to media hosts. Pairing should create a per-device random token shown once, store only a token hash centrally, support revocation/rotation, and scope each token to that device. Tailscale HTTPS can carry Rawrarr web/API, control, and app-data traffic when the services are private to the tailnet. Tailscale is not a media transport: heartbeats and scan uploads must never include API keys, absolute media paths, or media bytes, and Rawrarr must not route media files or streams through it.

## Cloud portal and public relay boundary (future)

The cloud portal should be an access and rendezvous service, not the application controller. It may authenticate a portal account, list authorized opaque instance/device IDs, and find online nodes. The self-hosted node remains responsible for the Rawrarr application, passkey authentication, authorization, and configuration access. Treat the relay as a routing control plane and an opaque byte-forwarding data plane, not as a reverse proxy that terminates application TLS. The Rawrarr node initiates and maintains an outbound authenticated tunnel so it can work behind NAT; the browser's TLS session must terminate at that node.

The portal/relay may retain account data needed for portal sign-in, an opaque stable `instance_id`, member `device_id`s, public keys needed to authenticate outbound connections, and public age recipients associated with the passkey-authenticated portal account. Public age recipients are not credentials. It will also need transient routing state such as which devices are online and which tunnel to use. Network metadata (source IP, connection times, bytes transferred, and likely a routable hostname or SNI) is visible to the relay even when payloads are encrypted; minimize retention and do not log payloads. Instance and device IDs are identifiers, not access credentials. Use short-lived, audience-bound routing tickets and enforce access at the node. The portal must not have a server-side admin channel into subscriber nodes. It must never receive a private age identity or decrypt subscriber app data; pass subscriber traffic through as end-to-end encrypted bytes without retaining a payload copy.

Serve the Rawrarr UI through the node's end-to-end encrypted session so portal/relay-controlled page code cannot inspect application responses. The portal may provide discovery or bootstrap navigation, but it must not serve executable UI code for a session that claims relay-blind privacy. Prefer direct peer connections when available and use the relay as fallback. This is a design constraint, not an implemented feature; TLS passthrough, certificates for instance hostnames, routing, abuse controls, and failure behavior remain to be designed and tested. See the [cloud access architecture](cloud-access-architecture.md) for the proposed component model.

## Current implementation and next step

The app exposes `/api/devices` with a persistent per-node ID and reports whether `RAWARR_LIBRARY_PATH` is configured. Boneyard nodes run a bounded scheduled scan once per day by default, beginning one day after startup, filling missing or changed file-derived metadata while skipping completed records. The owner can also request a full scan or a bounded sample from the Devices view; owner-authenticated direct and coordinator relay routes expose only the scan request and status. Scan status reports `filesCompleted` and `filesTotal`, updating after each media file finishes, so the Devices view can show progress such as “1 of 3”. The boneyard hashes and probes media locally, encrypts sidecars with the shared public age recipient, and writes ciphertext under `/shared/metadata/library/text/`. A node-local cache stores opaque path fingerprints under `/data`; media bytes and relative paths do not leave the boneyard. The separate `storage-scan-once` utility remains available without PostgreSQL or web startup. Durable cross-node catalog reconciliation remains planned. See the [roadmap](../ROADMAP.md) and the [Tailscale plan](tailscale-integration-plan.md) for remaining multi-node work.

See the [roadmap](../ROADMAP.md) for the next implementation milestone and the remaining multi-node work. The boundary in this guide remains: a web host must never gain direct access to another node's media filesystem, and the future public relay must not become a trusted Rawrarr application server.
