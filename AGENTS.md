# Rawrarr project instructions

- Keep all Rust code memory-safe. Do not introduce `unsafe` blocks.
- Keep the service node separate from subscriber nodes. Never place private age identities, passkeys, credentials, media, or subscriber app-data in the service-node or relay code paths.
- Treat `/shared` as synchronized application data, `/media` as node-local media, and `/data` plus PostgreSQL as node-local state. Never commit runtime data, local databases, secrets, `.env` files, or age identities.
- Use the `.ev` suffix on Rawrarr folder names to mean "eventually": a placeholder or planned folder that is not in active use. It is also a nod to Will's Chevy Bolt EV. Do not add `.ev` to active runtime paths or rename an existing folder just to apply the convention.
- Preserve existing and concurrent work. Before editing, inspect `git status --short --branch` and `git worktree list`. Treat changes in a shared checkout as potentially belonging to another task unless ownership is clear; never reset, stash, discard, or stage them wholesale. Each task may commit only changes it made for its own issue; leave changes made by other tasks in the same checkout untouched and uncommitted by this task. Stage only explicit paths or hunks owned by this task, review the staged diff to confirm it contains no other task's changes, and commit task-owned changes in focused commits as meaningful milestones are completed. A task may commit even when that leaves the working tree clean; do not wait for a final bundle of unrelated tasks.
- Prefer one issue or cohesive change per task, and carry that change through gradually in small, reviewable increments. When tasks are likely to edit the same repository at the same time, or overlapping ownership cannot be safely separated in one checkout, use a dedicated Git worktree for each task. Worktrees should let each task implement and commit its own incremental progress without colliding with other tasks' edits; they are an isolation aid for focused work, not a reason to combine unrelated issues into one task. Reuse an existing task worktree when suitable; otherwise create one from the intended base branch/ref, and do not copy or overwrite concurrent working-tree changes. Work in the returned worktree path. Keep each task's commits scoped only to its own issue and changes; do not include another task's commits in a push unless they are already part of the shared upstream history. Push only when the branch has an upstream and all outgoing commits belong to the task; never force-push, create a remote, merge branches, or rewrite shared history. If worktrees are unavailable or would disrupt another task, continue only with clearly separable changes in the shared checkout.

## Local Compose rebuilds

- Serialize deployments per container with hidden, local-only markers in `~/Library/Application Support/Rawrarr/`, alongside (but never inside) `shared-data`. Use a distinct marker for each Compose container/service, named `.container-rebuild-<container-name>.lock` (for example, `.container-rebuild-roarlay.lock`, `.container-rebuild-fossil.lock`, or `.container-rebuild-boneyard.lock`). These runtime files must never be added to or committed in Git. Before rebuilding, restarting, recreating, or otherwise deploying a container, check its marker. If it exists, another task owns that container's deployment: wait and periodically recheck until it is removed; do not change that container while waiting, and do not remove another task's marker. A task may deploy a different container concurrently, provided it does not restart or otherwise disrupt the container locked by another task.
- Before starting a container deployment, claim that container's marker atomically so two tasks that checked at nearly the same time cannot both proceed: `(set -C; : > "$HOME/Library/Application Support/Rawrarr/.container-rebuild-<container-name>.lock")`, substituting the actual Compose service/container name. If creation fails because the file already exists, wait; do not truncate or remove it. After successful creation, confirm the marker exists and treat it as this task's deployment lock. Keep it present throughout build, restart, and health/route verification steps that affect that container. When that container's deployment work is complete—or has failed and no more work on it will be attempted—remove its marker and confirm it is gone so another task can proceed. Never put markers under `/shared` or its host `shared-data` directory, since that directory is synchronized.
- This shell may not have `RAWARR_POSTGRES_PASSWORD_FILE` set, so a plain `docker compose up` can fail during Compose interpolation before touching containers. For the persistent local deployment, use the existing protected password file at `~/Library/Application Support/rawrarr/orbstack-postgres-password` and pass its path inline without reading or printing its contents:
  `RAWARR_POSTGRES_PASSWORD_FILE="$HOME/Library/Application Support/rawrarr/orbstack-postgres-password" docker compose -p rawrarr-local up -d --build roarlay`
- Always use Compose project `rawrarr-local` when updating that deployment. Omitting `-p rawrarr-local` can create a separate project with new volumes, and its attempt to bind 127.0.0.1:7297 will conflict with the real service. Do not stop or remove the existing service or volumes to work around the conflict.
- If the documented password file is missing, inspect the running `rawrarr-local` app container’s Compose metadata and secret mount for the configured path. Keep the secret value out of output and do not guess a replacement.
- Before rebuilding, verify which process/container owns port 7297. After rebuilding, confirm the `rawrarr-local` app is healthy and `http://127.0.0.1:7297/health` responds successfully.

## Tailnet coordinator URL

- `https://rawrarr.risk-mermaid.ts.net/` and `/health` must route to the internal coordinator roarlay on Brandon's Mac mini, never to the MacBook fossil. Roarlay shares the `rawrarr-internal-mini` Tailscale sidecar network namespace, so Tailscale Serve HTTPS 443 proxies directly to `http://127.0.0.1:8080`. The Tailscale service publishes coordinator diagnostics only on host loopback `127.0.0.1:7298` and carries the Docker network alias `coordinator`; preserve both when changing the Compose layout. No Caddy coordinator proxy is needed.
- Syncthing peer traffic uses a separate Tailscale Serve TCP forward on port 22000 directly to the Syncthing container's port 22000. Do not add a TCP bridge container for it. The Syncthing GUI remains loopback-only on port 8385 and has no Tailscale Serve web handler unless one is deliberately configured.
- After any internal coordinator Compose, Tailscale sidecar, or Serve change, read back `docker exec rawrarr-internal-mini-tailscale-1 tailscale serve status --json` on the Mac mini and confirm `rawrarr.risk-mermaid.ts.net:443` `/` proxies to `http://127.0.0.1:8080`. Then verify `curl -fsS https://rawrarr.risk-mermaid.ts.net/health` succeeds and identifies roarlay. A container's healthy status or a local-only health check does not verify this route.
- If Serve status points elsewhere, restore it with `docker exec rawrarr-internal-mini-tailscale-1 tailscale serve --bg --yes --https=443 http://127.0.0.1:8080` on the Mac mini, then repeat both read-back and HTTPS checks. Preserve unrelated Serve handlers and TCP forwards; do not use `tailscale serve reset`.

## Waiting for a container deployment lock

- If a requested container rebuild, restart, recreation, or deployment is blocked because that container's deployment marker already exists, wait one minute and check the marker again. Keep repeating at one-minute intervals until the marker is gone, then atomically claim it and continue the requested deployment. Do not interrupt the task that owns the marker or remove its marker. After acquiring the lock, complete the deployment and verify the requested result before releasing it. If the user asks for this retry behavior, continue waiting until the lock is available or the user changes the instruction.
