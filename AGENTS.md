# Rawrarr project instructions

- Keep all Rust code memory-safe. Do not introduce `unsafe` blocks.
- Keep the service node separate from subscriber nodes. Never place private age identities, passkeys, credentials, media, or subscriber app-data in the service-node or relay code paths.
- Treat `/shared` as synchronized application data, `/media` as node-local media, and `/data` plus PostgreSQL as node-local state. Never commit runtime data, local databases, secrets, `.env` files, or age identities.
- Preserve existing user changes. Before editing, inspect `git status --short --branch`. Save changes made only by this task into Git as work progresses; leave other unrelated changes alone. Stage explicit task-owned files or hunks and review the staged diff before committing. If a proposed commit would leave no uncommitted changes, stop and tell Will instead of making that commit.
- For substantive implementation or operations work, create a dated task runbook in `runbooks/` and update its index. Keep design decisions in `docs/DESIGN.md`, architecture in the relevant technical document, and mark unimplemented behavior as planned.
- Maintain tests for meaningful behavior changes under `scripts/tests/`; update their index. Run focused checks for the affected behavior and state clearly what was not verified.
- Keep Rawrarr-specific project work in this repository. Do not import unrelated Arr-services scripts, operational runbooks, service configuration, or media files.
- In the local environment, always publish the `rawrarr-local` web service on `127.0.0.1:7297` (RAWR on a telephone keypad). Use this port for local Rawrarr access and keep the local WebAuthn origin aligned with it. Before starting or moving the service, check whether port 7297 is occupied. If another process or container owns it, identify and resolve that conflict before continuing; do not silently choose another port.

- When Will asks for a Rawrarr web UI change without naming a node, treat the roarlay UI at `https://rawrarr.risk-mermaid.ts.net/` as the target. Implement and deploy the change in the roarlay container; do not deploy it to the metadata or storage nodes unless Will explicitly identifies one of those nodes.
- After roarlay UI changes, update the `roarlay` container in the existing `rawrarr-local` Compose project and verify roarlay health and the tailnet route as described below. Preserve existing data, configuration, and the user’s browser windows.

## Local Compose rebuilds

- Serialize deployments per container with hidden, local-only markers in `~/Library/Application Support/Rawrarr/`, alongside (but never inside) `shared-data`. Use a distinct marker for each Compose container/service, named `.container-rebuild-<container-name>.lock` (for example, `.container-rebuild-roarlay.lock`, `.container-rebuild-metadata.lock`, or `.container-rebuild-apex.lock`). These runtime files must never be added to or committed in Git. Before rebuilding, restarting, recreating, or otherwise deploying a container, check its marker. If it exists, another task owns that container's deployment: wait and periodically recheck until it is removed; do not change that container while waiting, and do not remove another task's marker. A task may deploy a different container concurrently, provided it does not restart or otherwise disrupt the container locked by another task.
- Before starting a container deployment, claim that container's marker atomically so two tasks that checked at nearly the same time cannot both proceed: `(set -C; : > "$HOME/Library/Application Support/Rawrarr/.container-rebuild-<container-name>.lock")`, substituting the actual Compose service/container name. If creation fails because the file already exists, wait; do not truncate or remove it. After successful creation, confirm the marker exists and treat it as this task's deployment lock. Keep it present throughout build, restart, and health/route verification steps that affect that container. When that container's deployment work is complete—or has failed and no more work on it will be attempted—remove its marker and confirm it is gone so another task can proceed. Never put markers under `/shared` or its host `shared-data` directory, since that directory is synchronized.
- This shell may not have `RAWARR_POSTGRES_PASSWORD_FILE` set, so a plain `docker compose up` can fail during Compose interpolation before touching containers. For the persistent local deployment, use the existing protected password file at `~/Library/Application Support/rawrarr/orbstack-postgres-password` and pass its path inline without reading or printing its contents:
  `RAWARR_POSTGRES_PASSWORD_FILE="$HOME/Library/Application Support/rawrarr/orbstack-postgres-password" docker compose -p rawrarr-local up -d --build roarlay`
- Always use Compose project `rawrarr-local` when updating that deployment. Omitting `-p rawrarr-local` can create a separate project with new volumes, and its attempt to bind 127.0.0.1:7297 will conflict with the real service. Do not stop or remove the existing service or volumes to work around the conflict.
- If the documented password file is missing, inspect the running `rawrarr-local` app container’s Compose metadata and secret mount for the configured path. Keep the secret value out of output and do not guess a replacement.
- Before rebuilding, verify which process/container owns port 7297. After rebuilding, confirm the `rawrarr-local` app is healthy and `http://127.0.0.1:7297/health` responds successfully.

## Tailnet coordinator URL

- `https://rawrarr.risk-mermaid.ts.net/` and `/health` must route to roarlay on the MacBook, never to the metadata node. Roarlay shares the `rawrarr-macbook-tailscale` network namespace, so Tailscale Serve HTTPS 443 proxies directly to `http://127.0.0.1:8080`. The Tailscale service publishes coordinator diagnostics only on host loopback `127.0.0.1:7298` and carries the Docker network alias `coordinator`; preserve both when changing the Compose layout. No Caddy coordinator proxy is needed.
- Syncthing peer traffic uses a separate Tailscale Serve TCP forward on port 22000 directly to the Syncthing container's port 22000. Do not add a TCP bridge container for it. The Syncthing GUI remains loopback-only on port 8385 and has no Tailscale Serve web handler unless one is deliberately configured.
- After any Compose, Tailscale sidecar, or Serve change, read back `docker exec rawrarr-macbook-tailscale tailscale serve status --json` and confirm `rawrarr.risk-mermaid.ts.net:443` `/` proxies to `http://127.0.0.1:8080`. Then verify `curl -fsS https://rawrarr.risk-mermaid.ts.net/health` succeeds and identifies roarlay. A container's healthy status or a local-only health check does not verify this route.
- If Serve status points elsewhere, restore it with `docker exec rawrarr-macbook-tailscale tailscale serve --bg --yes --https=443 http://127.0.0.1:8080`, then repeat both read-back and HTTPS checks. Preserve unrelated Serve handlers and TCP forwards; do not use `tailscale serve reset`.

## Waiting for a container deployment lock

- If a requested container rebuild, restart, recreation, or deployment is blocked because that container's deployment marker already exists, wait one minute and check the marker again. Keep repeating at one-minute intervals until the marker is gone, then atomically claim it and continue the requested deployment. Do not interrupt the task that owns the marker or remove its marker. After acquiring the lock, complete the deployment and verify the requested result before releasing it. If the user asks for this retry behavior, continue waiting until the lock is available or the user changes the instruction.
