# Rawrarr technical status

> Current container architecture: **roarlay** (`coordinator`) owns passkeys and node coordination; **fossil** (`metadata`) serves encrypted app data and Arr connections; **boneyard** (`storage`) reads local media. See [container deployment](container-deployment.md). Owner-approved pending enrollment is implemented; browser device-code linking remains planned.

Last reviewed: 2026-10-18.

The [roadmap](../ROADMAP.md) is the source of truth for completed and outstanding work. This page records the architectural constraints that apply across current and future features. See the [user guide](user-guide.md) for current usage and the [runbook index](../runbooks/README.md) for dated implementation evidence.

## Data and trust boundaries

- `/media` is read-only in each Rawrarr boneyard worker. An owner-selected Syncthing media share can separately copy a chosen source directory to an approved second boneyard node; its source mount is read-only and its destination Syncthing mount is writable. Roarlay, Tailscale web routes, and `/shared` do not carry media bytes as app data.
- `/shared` is the Syncthing app-data root. `/metadata` aliases `/shared/metadata`. Metadata is grouped by type and content kind, such as `/metadata/movies/text/` and `/metadata/movies/artwork/`; generic library sidecars are under `/metadata/library/text/`. `config.aged` and metadata ciphertext sync, while logs are compressed and allowlisted but not age-encrypted individually. Local Compose can maintain a mode-`0600` Radarr settings mirror in node-local `/data`; production disables and removes that mirror.
- `/data` and the live PostgreSQL database are local to each container/node. A Syncthing copy of files is not database replication or quorum.
- Production Syncthing peer and folder setup is gated on explicit owner approval of the joining Rawrarr node. The already-paired Mac mini/MacBook Syncthing devices have one `rawrarr-media` share rooted at `/media` (their music directories), filtered to top-level A/a artists and three explicitly selected albums in other artist directories, in addition to `rawrarr-shared`. Its Syncthing connection is pinned to Tailscale TCP 22000 through userspace SOCKS5 with no direct fallback; discovery and public relays are disabled for this pair. This does not imply automatic sharing for later nodes. A separate MacBook storage worker is pending owner approval, so its media scan and catalog entry are not yet active.
- The operator's relay/service node may store account credentials, public age recipients, billing/license status, and opaque instance/device IDs. It must never receive private age identities or subscriber app-data plaintext.

## Current-source and runtime status

These descriptions reflect the current checkout. Dated runbook tests and deployment results apply only to their recorded task; source behavior alone does not establish the currently running image or live integration state.

Roarlay shows passkey sign-in while anonymous and the owner workspace after sign-in. The workspace has Overview, Devices, Movies, TV, Configuration, Settings, and About views. It lists owner-authorized nodes, probes a scoped direct Tailscale route from the browser, and falls back to a coordinator relay when direct access fails. The full Movies and TV inventories use a per-request encrypted response that the browser decrypts; shared movie metadata export uses age ciphertext and browser-side decryption. Roarlay must not receive private age identities or media. The browser can keep the age private ID for the tab or, by explicit opt-in, persist it in browser storage; sign-out clears the in-memory ID. The [blind coordinator content flow](blind-coordinator-content.md) describes remaining limits. `/health` remains an HTML web-process liveness page, not proof of database, Arr, or peer readiness.

The source implements owner approval for joining nodes, a direct route probe and relay fallback, on-demand metadata rescans, all-indexed-movie browser export, and periodic storage scans. The export currently builds the ZIP in browser memory; periodic scans first run after one configured interval. A [dated bounded Mini scan](../runbooks/2026-10-18-clarify-storage-scan-action.md) produced three synchronized encrypted sidecars, and a [later Mini update](../runbooks/2026-10-18-update-mac-mini-containers.md) rebuilt storage. Neither runbook observed an unattended scheduled scan. Recheck image IDs, service health, authenticated pages, and tailnet routes before claiming a current deployment result.

### Sonarr initial integration

Implemented authenticated Sonarr status, encrypted connection settings (read/save/clear), and read-only series inventory using the v3 API (Sonarr 3/4). The coordinator Settings form sends the age identity and Sonarr credentials directly from the browser to the selected fossil node; the coordinator relay does not accept or forward Sonarr settings. Shared library columns serve Radarr and Sonarr, and both pages use one configurable four-card summary renderer with service-specific labels and detail text. The coordinator TV page reads the configured Sonarr series inventory directly from the selected fossil node and displays series, episode counts, TVDB ID, monitoring, year, quality profile, disk size, and the size of the encrypted TV metadata subtree alongside total shared metadata size. Fossil nodes scrape uncached Sonarr series metadata and posters into separate HMAC-named age-encrypted `tv/text/` and `tv/artwork/` folders sequentially after first connection and every six hours. The TV page hides completed-backfill and successful-load messages once every eligible poster is saved, even while the worker checks for newly added series. Metadata search and episode mutations remain planned.
